                            NVIM REFERENCE MANUAL


==============================================================================
wgvim                                           *wgvim* *wgvim-differences*

wgvim is an offline, hardened build of Neovim (|nvim|). Neovim, and Vim
before it, are the work of their contributors; wgvim only removes and
restricts features. See |credits| and the NOTICE file for the full origin
and licence. Please do not report wgvim problems to the Neovim project.

Everything not listed here works as described in the rest of this manual.

                                      Type |gO| to see the table of contents.

==============================================================================
No network access                                       *wgvim-network*

The editor itself makes no network connections:

- |vim.net| and the "http(s)://" buffer reader are removed.
- |vim.pack| (which used `git`) is removed. Copy plugins into a
  "pack/*/start/" or "pack/*/opt/" directory instead (|packages|).
- Spell files are not downloaded (|spell-SpellFileMissing|). English is
  bundled.
- |netrw| works only on local files and "file://" URLs.
- RPC servers (|--listen|, |serverstart()|) and |sockconnect()| accept only
  pipes and Unix-domain sockets, not TCP. LSP servers are started over stdio
  or a pipe (|vim.lsp.rpc.connect()| refuses a port).
- `vim.uv` has no TCP, UDP or DNS functions.

Programs you start (|:!|, |jobstart()|, |vim.system()|, |:terminal|, LSP
servers) cannot make or accept TCP connections either when the |wgvim-sandbox|
is active and the kernel supports it (Landlock ABI 4, Linux 6.7). UDP is not
covered. For a hard guarantee, run wgvim without network access at the
operating-system level.

==============================================================================
Restricted features                                     *wgvim-restricted*

- No server is started at startup; |v:servername| is empty unless |--listen|
  is given or |serverstart()| is called.
- 'exrc' and 'modelineexpr' are always off and cannot be set (E519).
- LuaJIT's `ffi` library is disabled, and native Lua modules (.so files)
  cannot be loaded (`package.loadlib()` raises an error).
- Treesitter parsers are loaded only from the install directory, and only
  the parsers bundled at build time, after checking their SHA256.
- `lsp/*.lua` configs are read only from |stdpath()| "config" and $VIMRUNTIME.
- Programs running in |:terminal| cannot set the system clipboard (OSC 52).
- |sockconnect()| always fails (E5435), and the |--remote| and |--server|
  arguments (including |--remote-ui|) are refused: wgvim does not connect to
  other processes' sockets. `serverlist({peer = v:true})` lists only this
  instance's servers. |:restart| and |:connect| still work: the terminal UI
  may connect to wgvim's own sockets in its temp directory.
- The Python 3, Ruby, Perl and Node.js providers and remote plugins are
  removed (|provider-python|, |remote-plugin|). The clipboard provider stays.

==============================================================================
Sandbox                                                 *wgvim-sandbox*

At startup, before any config or plugin runs, wgvim confines itself with the
Linux Landlock security module. The restriction cannot be lifted afterwards:
not by a plugin, a modeline or an exploited bug, and not by the programs wgvim
starts (|:!|, |:terminal|, jobs, LSP servers), which are confined too.

What it allows:

  Read-write, and execute ~
  - The current directory and everything below it.
  - Files and directories named on the command line: a file gives access to
    that file only, a directory to everything below it. A new file that does
    not exist yet can only be created inside the current directory.
  - Paths given with |--sandbox-allow|.
  Read-write ~
  - |stdpath()| "state" and "cache" (ShaDa, swap, undo and backup files, logs)
    and the temp directory ("/tmp/wgvim.<user>/").
  - "~/.cache/clangd", when clangd is installed (its index for files outside
    a project; the index of a project goes to ".cache/clangd" in the project).
  Read and execute ~
  - "/usr", "/bin", "/sbin", "/lib", "/lib64", "/opt", the directory of the
    wgvim executable, "~/.local/bin", "~/bin", and |--sandbox-allow-ro| paths.
  Read-only ~
  - "/etc", "/proc", "/sys", |stdpath()| "config" and "data" (your config and
    installed plugins), $VIMRUNTIME, the parser directory, $XDG_CONFIG_DIRS
    and $XDG_DATA_DIRS.
  - A few files that shells, git and clangd read: "~/.bashrc",
    "~/.bash_profile", "~/.profile", "~/.inputrc", "~/.gitconfig",
    "~/.config/git", "~/.config/clangd", "~/.clang-format", "~/.clang-tidy",
    "~/.editorconfig".
  Devices ~
  - "/dev/null", "/dev/tty", your terminal, and "/dev/ptmx" and "/dev/pts"
    for |:terminal|.

Everything else is refused: other people's projects, "~/.ssh", "~/.gnupg",
browser profiles, and so on. When the sandbox refuses a file, the error says
so, e.g. "E212: Can't open file for writing: permission denied (outside the
wgvim sandbox, see :help wgvim-sandbox)".

Besides the Landlock file rules, a system call filter (seccomp) is installed
at the same time and inherited the same way. It allows only Unix sockets (no
TCP, UDP, ICMP, raw, packet or netlink sockets), refuses connect() and
sendto() with an address, so that existing sockets such as the D-Bus bus
("/run/user/<uid>/bus", through which "systemd --user" would run commands
outside the sandbox), ssh-agent and gpg-agent cannot be reached, and refuses
System V IPC (shared memory, semaphores, message queues) and io_uring. The
terminal UI process alone may connect, and only to wgvim's own sockets in its
temp directory (for |:restart| and |:connect|); see |wgvim-sandbox-tui|.

                                                *wgvim-sandbox-tui*
wgvim in a terminal is two processes: the terminal UI (TUI) and the editor.
The TUI applies the sandbox to itself and then starts the editor, which
applies it again, a second and stricter layer, before it reads your config.
Everything the editor runs (|:!|, |:terminal|, LSP servers) is inside both
layers. The TUI is inside the first only, and it is the more privileged of
the two: it may connect() to sockets (the filter cannot tell which), and
wgvim's own code then allows only its sockets, for |:restart| and |:connect|.
Programs inside the editor's layer cannot trace the TUI, nor (from Linux
6.12) signal it.
The TUI reads everything the editor sends it to draw the screen. So a
compromised editor that also found a flaw in that drawing code could take
over the TUI, and with it the right to connect(), for example to the D-Bus
bus and from there outside the sandbox. That takes two flaws, and the second
must be in a small part of the code; it is accepted for now. Without the TUI
(|--headless|, or |--embed| behind another UI), only the clipboard helper
may connect.

When the kernel supports it, Landlock also blocks TCP (ABI 4, Linux 6.7), and
connections to abstract Unix sockets and signals to processes outside the
sandbox (ABI 6, Linux 6.12): wgvim and the programs it starts can signal each
other, but not your other processes. Landlock always keeps sandboxed
processes from tracing (ptrace) processes outside the sandbox.

                                                *wgvim-sandbox-home*
Starting wgvim in your home directory gives access only to its entries that
are not hidden ("~/notes.txt", "~/projects/", but not "~/.ssh" or
"~/.bashrc"), and a new file cannot be created there. Starting it in "/" or
in a top-level directory that contains home directories ("/home") gives no
write access to the current directory at all. If your home directory is
inside a deeper current directory (as some test setups do), it is reachable
like the rest of that directory. Start wgvim inside the project you work on.

Things that work differently ~
- ":e" and ":w" outside the current directory fail, unless the file was named
  on the command line. Use |--sandbox-allow| for another directory.
- Setuid programs cannot gain privileges ("no new privileges"), so ":!sudo"
  and ":w !sudo tee %" do not work.
- `:!kill` cannot stop or signal your other processes (Landlock ABI 6+).
- The clipboard (|clipboard|): wl-copy, xclip and xsel need to connect to the
  display server, which the sandbox refuses. On a local desktop
  ($WAYLAND_DISPLAY or $DISPLAY set, not over SSH) wgvim starts a clipboard
  helper just before the sandbox is applied. The helper is not confined by
  Landlock and may connect, and does one thing: it runs the fixed copy or
  paste command of the tool it found (wl-copy/wl-paste, else xclip, else xsel)
  for "+" or "*" with the text it is given. The tool is looked up once, at
  startup, and is not used if it is in a directory the sandbox can write to
  (such as a project directory in $PATH), since a sandboxed program could have
  put it there. The editor can only ask it to set or read the clipboard. Over
  SSH, copying uses OSC 52 (|clipboard-osc52|), and pasting "+" returns what
  was last copied in wgvim: many terminals cannot answer OSC 52 reads, and
  waiting for them stalls every paste. Paste from the system clipboard with
  the terminal's own paste instead (mintty: Shift+Insert; copying needs
  "AllowSetSelection=yes" in ~/.minttyrc). tmux's clipboard is not available.
  |:checkhealth| wgvim shows which applies.
- Child programs get $TMPDIR set to the temp directory above, because "/tmp"
  itself is not writable (compilers and clangd write temporary files there).
- Swap, undo and backup files are written to their default directories in
  |stdpath()| "state". A config that sets 'undodir', 'directory' or
  'backupdir' elsewhere (e.g. "~/.vim/undodir") gets E828 and similar errors;
  remove the setting, or use |--sandbox-allow|. |:checkhealth| wgvim warns
  about it.
- Your config directory is read-only, so editing "init.lua" in wgvim needs
  wgvim to be started in "~/.config/wgvim", or |--sandbox-allow|.
- A shell in |:terminal| cannot read most dotfiles and cannot write its
  history file.
- clangd: system headers and the project are readable. Include directories
  outside both (from "compile_commands.json") need |--sandbox-allow-ro|, and
  an index for a project whose root is above the current directory is not
  saved.

                                                *wgvim-sandbox-git*
The project's ".git" directory stays writable, like the rest of the project.
Git runs commands named in ".git/config" (core.pager, core.fsmonitor,
aliases, filters, credential helpers) and the scripts in the hooks directory,
and it runs them outside the sandbox, the next time you use git there: a
plain "git status", which many shell prompts run on their own, is enough. So
a sandboxed program that wrote there would get out of the sandbox later.
Landlock cannot make one subdirectory read-only inside a writable tree, so
wgvim cannot prevent the write. It detects it instead:

- At startup, before the sandbox is applied, wgvim starts a small watcher
  process outside it. It records ".git/config", ".git/config.worktree", the
  hooks, a "core.hooksPath" directory (such as ".husky" or ".githooks"),
  files named by "include.path", and the same for submodules and linked
  worktrees. It only reads them (never following symlinks); it runs nothing.
- When wgvim exits, the watcher compares, and prints to the terminal each
  file that was added, removed or changed, with the lines added to a config
  file. Names and lines are printed with control characters replaced.
- Sandboxed programs cannot trace or (from Linux 6.12) signal the watcher.
  On older kernels they could kill it; wgvim then says at exit that the
  check did not run.

If you see the warning and did not make the change yourself (git remote add,
git branch -u and installing hooks all change these files), check the listed
files before you run git in that project again, e.g. with
"git config --list --show-origin" and "ls -la .git/hooks". The warning does
not stop the change, and it only comes at exit: git run in another terminal
while wgvim is open is not protected. |:checkhealth| wgvim shows what is
watched. Only the repository in the working directory is watched (not other
repositories below it), and only when wgvim is not running with |--embed|
behind another UI.

Some files in the project itself also run outside the sandbox, at your
request rather than git's: build scripts, and hook frameworks (husky,
pre-commit, lint-staged) that run project scripts from a hook. Review changes
to those as you would any change to the code.

Limits ~
- Landlock needs Linux 5.13 or later; on RHEL 9 it is available from 9.6.
  On a kernel without it, wgvim starts unconfined unless "--sandbox require"
  is given. Older Landlock versions do not control truncating files (ABI 3),
  and with ABI 1 renaming files across directories is refused outright.
- Other terminals of the same user under "/dev/pts" can be written to.
- On kernels before Linux 6.12 (Landlock ABI 6), processes outside the sandbox
  can be signalled.
- Programs that need to reach a Unix socket outside the sandbox fail: for
  example a name lookup that misses SSSD's cache (an LDAP user's name may
  show as a number in "ls -l"), or logging to syslog. Python's
  multiprocessing needs "/dev/shm", which is not allowed.
- The system call filter is built for x86-64 and AArch64 only.
- ".git" is writable; changes to it are reported at exit, not prevented
  (|wgvim-sandbox-git|).
- The terminal UI process may connect() to sockets (|wgvim-sandbox-tui|).
- The policy is fixed at startup. A directory created later, or a file named
  in |:cd|, |:e| or a plugin, gets no extra access.

Use |:checkhealth| wgvim to see whether the sandbox is active and its rules.
The test suite and the build turn it off ($WGVIM_SANDBOX=off).

                                                *--sandbox*
--sandbox {mode}
		"on" (the default), "off", or "require": like "on", but exit if
		the kernel cannot apply the sandbox. Without this argument the
		mode is taken from $WGVIM_SANDBOX. A sandbox that is already
		active (wgvim started from a confined wgvim) cannot be turned off.

                                                *--sandbox-allow*
--sandbox-allow {path}
		Also allow reading, writing and running programs below {path}.
		Can be repeated.

                                                *--sandbox-allow-ro*
--sandbox-allow-ro {path}
		Also allow reading and running programs below {path}. Can be
		repeated.

SELinux policy                                          *wgvim-selinux*

The sandbox is applied by wgvim itself. An SELinux policy module, in
"contrib/selinux/", adds a layer that the kernel applies to the installed
binary whatever wgvim's code does: the editor and everything it starts run in
the "wgvim_t" domain, which may use the user's ordinary files in $HOME and
/tmp, read system files and run programs, but has no network sockets, cannot
connect to other domains' Unix sockets (D-Bus, ssh-agent, gpg-agent), cannot
read "~/.ssh" or "~/.gnupg", and cannot signal other domains or use
capabilities. It confines the installed binaries ("/usr/bin/wgvim",
"/usr/local/bin/wgvim", "/opt/wgvim/bin/wgvim"); a binary in a source tree
only with "--binary".

Install it as root with "scripts/wgvim-selinux.sh install". It starts in
permissive mode: denials are logged, nothing is blocked. After using wgvim
for a while, "scripts/wgvim-selinux.sh denials" shows what would have been
refused; "scripts/wgvim-selinux.sh enforce" turns it on. "status" and
"uninstall" do what they say. Needs selinux-policy-devel and
policycoreutils-python-utils.

Reading aids                                            *wgvim-reading*

Optional aids that make the structure of code easier to follow. All are off
until turned on, from the config: >lua
    require('wgvim.reading').setup({
      rainbow = true,     -- colour brackets by nesting level
      scope = true,       -- line along the block around the cursor
      references = true,  -- highlight the symbol under the cursor
      context = true,     -- show the function/block heading at the top
    })
<
or for the session with |:Reading|.

Rainbow delimiters                                      *wgvim-rainbow*
	Brackets ("()", "[]" and "{}") are coloured by how deeply they are
	nested, so the two brackets of a pair
	always have the same colour. Uses the buffer's |treesitter| parser, so
	brackets in strings and comments are left alone; buffers without a
	parser are not coloured. Seven colours from the Okabe-Ito palette,
	which stays distinguishable with the common forms of colour blindness.
	To turn it off for one buffer (in an ftplugin, say): >lua
	    require('wgvim.reading').rainbow_buf(0, false)
<
Scope guide                                             *wgvim-scope*
	A thin line ("│") down the left edge of the indented block that holds
	the cursor, from the line that opens it to the line that closes it.
	Based on indentation, so it works in any file type. The character is
	set with `scope_char` in setup().

Reference highlighting                                  *wgvim-references*
	After the cursor rests ('updatetime') on a word, the other places it
	occurs are highlighted until the cursor moves. With a language server
	that supports it (clangd does) only real references to the same symbol
	are marked; otherwise every whole-word match in the window.

Context                                                 *wgvim-context*
	When the first line of the function, loop or other block that the top
	of the window is in has scrolled off screen, it is shown over the
	window's first lines, with the line number and the colours of the
	original, and underlined to set it apart. Nested blocks give one line
	each, up to `context_max` (default 3: the outermost and the innermost
	ones). Uses the |treesitter| parser when the buffer has one, otherwise
	indentation; a line with only "{" is skipped for the one before it.
	Hidden while the cursor is on a line it would cover. To jump to the
	innermost line shown: >lua
	    vim.keymap.set('n', '<Leader>k', require('wgvim.reading').context_jump)
<
							*:Reading*
:Reading		Show which aids are on.
:Reading {aid} [on|off|toggle]
		Turn "rainbow", "scope", "references" or "context" on or off;
		without the last argument, toggle it.

Highlight groups, set by a colour scheme or with |nvim_set_hl()|:
	WgvimRainbow1 .. WgvimRainbow7	bracket colours, outermost first
	WgvimScope			the scope guide (default: links to Comment)
	WgvimReference			reference highlighting (default: links to
					LspReferenceText)
	WgvimContext			the context lines (default: links to
					NormalFloat)
	WgvimContextLineNr		their line numbers (default: links to LineNr)
	WgvimContextBottom		their last line (default: underlined)

Other settings that help reading are part of Vim already, for example
'cursorline', 'scrolloff', 'linespace' (GUI only) and a "leadmultispace" entry
in 'listchars' for indent guides.

==============================================================================
Names                                                   *wgvim-names*

The executable is `wgvim`. Per-user directories and environment variables use
"wgvim" / "WGVIM" instead of "nvim" / "NVIM": for example the config directory
is "~/.config/wgvim" and the log file is set with $WGVIM_LOG_FILE. Internal
names used by plugins (the `nvim_*` API, the `vim` Lua module) are unchanged.
